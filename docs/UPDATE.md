# Процедура обновления клиентского проекта

> Основание: ADR-0009, `docs/phase0/04-update-strategy.md` §4.2.8. Ниже: выпуск
> релиза шаблона (мейнтейнер), обновление клиентского проекта, раскатка
> security-релиза и hotfix для отставшего проекта.

## Выпуск релиза шаблона (мейнтейнер)

1. Версия — в трёх местах, одинаково: `pyproject.toml` (`version`),
   `shared/__init__.py` (`TEMPLATE_VERSION`), верхний раздел `CHANGELOG.md`
   (`## [X.Y.Z]`). Их согласованность держит `tests/test_versioning.py`: по
   `TEMPLATE_VERSION` CI клиента (`template-drift`) находит тег влитого релиза —
   рассинхрон направляет проверку дрейфа не на тот тег. Затем `uv lock`.
2. В `CHANGELOG.md` — разделы по keep-a-changelog и **Upgrade notes**: миграции,
   новые переменные окружения, ломающие изменения API и публичных интерфейсов.
   Security-пункты помечаются `[SECURITY]`.
3. `make lint && make test` зелёные → коммит → аннотированный тег
   `git tag -a vX.Y.Z -m "<что внутри>"`.

## Предусловия

- Проект создан клоном шаблона: remote `template` существует
  (`git remote -v`), история общая. Копия файлов без истории —
  антипаттерн, merge работать не будет.
- `CUSTOMIZATIONS.md` в корне проекта актуален (все помеченные
  `# CUSTOM(<project>)` правки шаблонных путей задекларированы).

## Шаги

1. `git fetch template --tags`
2. Прочитать в `CHANGELOG.md` шаблона раздел нового релиза, особенно
   **Upgrade notes** (и всех промежуточных релизов, если проект отставал).
3. `git merge --no-ff vX.Y.Z`
   - Конфликтов нет → шаг 4.
   - Конфликт в шаблонном пути → это сигнал: кастомизацию выносим из ядра
     (своя фича-папка, конфиг, событие шины) либо отправляем upstream в
     шаблон. Правка по месту — крайний случай, только с маркером
     `# CUSTOM(<project>): <причина>` и записью в `CUSTOMIZATIONS.md`.
   - `merge --squash` и rebase поверх влитых тегов **запрещены** —
     уничтожают общего предка (ловится CI-проверкой предка).
4. `git push origin vX.Y.Z` — тег обязан попасть в origin: по нему работает
   CI-джоба `template-drift`.
5. `uv sync`
6. `make migrate` (= `alembic upgrade heads` — все ветки) на dev-БД.
7. `make lint && make test`
8. Smoke: `GET /health`, `GET /ready` на dev-стенде.
9. push → deploy по процедуре проекта.
10. Отметка в реестре проектов: версия, дата merge, дата deploy
    (merge ≠ deploy; реестр — единственный источник ответа «фикс в проде»).

## Раскатка security-релиза по проектам

Релиз с пунктами `[SECURITY]` раскатывается на ВСЕ клиентские проекты, не «при
случае»:

1. Составить список проектов и версий шаблона в каждом (реестр проектов).
2. Для каждого — процедура выше (шаги 1–10); приоритет — проекты в проде с
   затронутой поверхностью (вебхуки, auth, приглашения и т.п. по CHANGELOG).
3. Проверить **Upgrade notes**: новые переменные окружения (prod-guard не даст
   стартовать без обязательных), миграции, ломающие изменения фронтенда —
   согласовать выкладку фронтенда в том же окне.
4. После деплоя — отметка в реестре (версия, дата deploy). Security-релиз
   считается раскатанным, когда у всех проектов в реестре стоит дата deploy.

## Hotfix для отставшего проекта

Если проект отстаёт на несколько релизов и полный merge сейчас невозможен:

1. Cherry-pick только коммитов `[SECURITY]` нужного релиза в ветку проекта
   (`git cherry-pick -x <sha>` — с ссылкой на исходный коммит).
2. Тесты, деплой, отметка в реестре «hotfix vX.Y.Z (cherry-pick)».
3. **Догоняющий merge** полного релиза — в течение 14 дней: cherry-pick не
   восстанавливает общего предка (`template-drift` его ищет), поэтому временное
   состояние нельзя оставлять.

Шаблон реестра проектов и read-only скрипт сверки версий — в бэклоге (`PLAN.md`).
