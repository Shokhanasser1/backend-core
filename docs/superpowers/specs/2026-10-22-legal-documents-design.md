# Документы и лицензирование — дизайн (утверждён владельцем 2026-10-22)

Три независимые части в порядке выполнения: (1) лицензия репозитория, (2) договоры
с клиентами, (3) модуль ядра `core/legal` — документы для пользователей клиентских
продуктов и фиксация их принятия. Тексты договоров и документов — черновики:
итоговую редакцию проверяет юрист в Узбекистане.

## Решения владельца

| Вопрос | Решение |
|---|---|
| Роль шаблона | Source-available: репозиторий публичный (портфолио), коммерческое использование — только по лицензии владельца |
| Лицензия репозитория | PolyForm Noncommercial 1.0.0 |
| Правообладатель | Пока не определён: в `LICENSE` — ник GitHub, в договорах — поля для реквизитов |
| Договоры с клиентами | Три отдельных: разработка, лицензионный, поддержка; ведутся вне репозитория |
| Репозитории клиентов (ОВ-34) | В организации владельца на GitHub, клиенту — зеркало |
| Поддержка (ОВ-36) | Абонентская: security-фиксы 24–48 ч, баги, обновления в пределах MAJOR |
| Продакшен | Сервер клиента в УЗ, администрирует владелец; клиент — оператор ПД, владелец — обработчик по поручению |
| Объём части 3 | Тексты-шаблоны ru/uz + модуль ядра для версий и фиксации принятия |
| Уровни документов | Платформа (регистрация) + организация (оферта продавца при заказе) |
| Тексты | Пользовательское соглашение (вкл. платную подписку), политика конфиденциальности, согласие на ПД, согласие на рассылки, публичная оферта продавца |
| Новая версия документа | Предупредить до даты вступления в силу, после неё — блокировать до принятия |
| Отзыв согласия на ПД | Фиксация + блокировка + уведомление владельцу платформы; удаление данных — вручную по регламенту |
| Хранение | Платформа — файлы в репозитории клиентского проекта, публикация при деплое; оферта — в БД через admin-экран |

## Часть 1. Лицензия репозитория

- `LICENSE` — официальный текст PolyForm Noncommercial 1.0.0 с Required Notice
  `Copyright (c) 2026 Shokhanasser1`.
- `pyproject.toml`: `license = "PolyForm-Noncommercial-1.0.0"` (SPDX).
- `README.md`: раздел «Лицензия» — бесплатно только некоммерческое использование,
  коммерческое — по отдельной лицензии, как связаться.
- `CHANGELOG`: версии до `0.15.1` включительно остаются под MIT (отозвать нельзя),
  с новой версии — PolyForm Noncommercial.
- Проверка лицензий зависимостей: допустимы MIT, BSD, Apache-2.0, ISC, PSF,
  LGPL (без модификации). Найденное иное — вопрос владельцу.
- Релиз `0.16.0` — до любого следующего push в публичный репозиторий.

## Часть 2. Договоры с клиентами

Ведутся вне репозитория: клиентский проект несёт полную git-историю шаблона, всё
лежащее здесь получил бы каждый клиент. В репозитории — только статусы ОВ-34 и
ОВ-36 в `docs/phase0/00-open-questions.md` (без цен и условий).

## Часть 3. Модуль `core/legal`

Модуль ядра по анатомии `core/billing`: `models.py`, `schemas.py`, `service.py`,
`router.py`, `permissions.py`, `admin.py`, `subscribers.py`, `cli.py`,
`migrations/` (ветка `core_legal`, `depends_on = "shared0002"`), `drafts/`,
`templates/` (уведомление), `README.md`. `CORE_MODULES` в `modules/loader.py`
пополняется `legal`.

### Данные

Уровни разведены по таблицам, чтобы RLS оставался простым.

**Платформа** (без `tenant_id`, доступ как к `users`):

| Таблица | Колонки | Права БД |
|---|---|---|
| `legal_platform_versions` | `key`, `version` (int), `locale`, `title`, `body`, `sha256`, `required` (bool), `effective_at`, `published_at`; уникально `(key, version, locale)` | `app_user` — SELECT; `app_maintenance` — SELECT, INSERT |
| `legal_platform_consents` | `user_id`, `key`, `version`, `locale`, `action` (`given` / `withdrawn`), `at`, `ip`, `user_agent` | `app_user` — SELECT, INSERT (журнал, без UPDATE/DELETE) |

`key` ∈ `terms`, `privacy`, `pd_consent`, `marketing`. Обязательные (`required`) —
задаются манифестом; по умолчанию `terms`, `privacy`, `pd_consent`.

**Организация** (`tenant_id` NOT NULL, `enable_tenant_rls`, FK на `tenants`
`ON DELETE RESTRICT`):

| Таблица | Колонки |
|---|---|
| `legal_tenant_versions` | `version` (int, NULL у черновика), `status` (`draft` / `published`), `body_ru`, `body_uz`, `sha256`, `published_at`; один черновик на тенант (partial unique), опубликованные неизменяемы |
| `legal_tenant_acceptances` | `version_id`, `user_id`, `order_id`, `at`, `ip`, `user_agent` (журнал) |

### Тексты и публикация документов платформы

- `core/legal/drafts/` — черновики шаблона: `terms`, `privacy`, `pd_consent`,
  `marketing`, `offer` × `ru`, `uz`; поля вида `{{company_name}}`;
  `requisites.example.toml`. Принадлежат шаблону, в клиентском проекте не правятся.
- `legal/` в корне клиентского проекта — его документы: `manifest.toml` (по ключу:
  `version`, `effective_at`, `required`), `requisites.toml`, `<key>/<locale>.md`.
- `python -m core.legal.cli init` — копирует черновики платформы и пример
  реквизитов в `legal/` (существующие файлы не перезаписывает).
- `python -m core.legal.cli publish` (роль `app_maintenance`, шаг деплоя после
  миграций): подставляет реквизиты; отказ, если нет пары ru/uz или осталось
  незаполненное поле; новая `version` → INSERT; та же `version` с тем же `sha256`
  → ничего; та же `version` с другим `sha256` → ошибка (опубликованное неизменяемо,
  поднимите версию). Событие `legal.document.published`.
- Узбекский черновик переводится при реализации; требует вычитки носителем языка.

### Регистрация

- `GET /api/legal/platform` (публичный) — актуальные документы и версии для формы.
- `RegisterIn` получает `accepted_documents: list[{key, version}]` и
  `marketing_opt_in: bool = False`. Нет хотя бы одного действующего обязательного
  документа → 422 `consent_required` (до создания пользователя). Создание
  пользователя и записи согласий — одна транзакция бандла.

### Блокировка при новой версии

- Проверка в общей зависимости `core/auth/deps.py`, открывающей бандл
  аутентифицированного пользователя (и `authed`, и `storefront`): если у
  обязательного документа есть версия с `effective_at <= now`, не принятая
  пользователем, или последнее действие по `pd_consent` — `withdrawn` →
  403 `consent_required` со списком `{key, version}`.
- Исключения — маркером роута `consent_exempt("reason")`: чтение и принятие
  документов, отзыв согласий, `/me`, logout, refresh.
- До `effective_at` блокировки нет: `GET /api/legal/me` возвращает `pending`
  (ключ, версия, дата вступления в силу) — фронт показывает окно.
- Стоимость: один индексный запрос на аутентифицированный запрос; кэш — только
  если замеры покажут необходимость.

### Согласия

- `POST /api/legal/accept` — принять документы (`{key, version}`, только
  действующие или вступающие в силу).
- `POST /api/legal/consents/marketing` `{granted: bool}` — в любой момент;
  публичный интерфейс `has_marketing_consent(user_id)` для будущих рассылок.
- `POST /api/legal/consents/pd/withdraw` — запись `withdrawn`, блокировка (см.
  выше), событие `legal.consent.withdrawn`; подписчик (reliable) шлёт уведомление
  `legal.pd_consent_withdrawn` (ru/uz) на `LEGAL_CONTACT_EMAIL` — платформенная
  отправка через maintenance UoW + `AddressRecipient`. Повторное принятие
  `pd_consent` снимает блокировку. Регламент ручного удаления данных — в README.
- `LEGAL_CONTACT_EMAIL` обязателен в production (валидация конфига).

### Оферта при заказе

- `GET /api/legal/offer` (storefront, `X-Shop-Tenant`, как остальная витрина по
  ОВ-39) — действующая оферта магазина.
- `CheckoutIn` получает обязательное `offer_version_id`. Публичный интерфейс
  `OfferAcceptance.accept(version_id, order_id)` вызывается `CartService.checkout`
  в той же транзакции, что и создание заказа: нет опубликованной оферты → 409
  `offer_missing`; версия не действующая → 409 `offer_outdated`.
- `modules/commerce/cart/feature.toml`: `requires_core += "legal"`. Событие
  `legal.offer.accepted`.

### Admin-экран организации

Slug `legal`: `GET /draft` (если черновика нет — предзаполнен из
`drafts/offer`), `PUT /draft`, `POST /publish` (обе локали, без незаполненных
полей; версия = предыдущая + 1, действует сразу), `GET /versions`.

### Права

`legal.document:read` (owner, admin), `legal.document:manage` (owner, admin).
Проверка на роуте и в сервисе (`PermissionGuard`). Роуты пользователя — маркер
`authenticated_endpoint`, их объект — сам актор.

### События

`legal.document.published`, `legal.consent.given`, `legal.consent.withdrawn`,
`legal.offer.accepted`. Payload — идентификаторы (ключ, версия, `user_id`,
`tenant_id`, `order_id`), без ПД. Публикация — после commit.

### Ошибки

Новые доменные ошибки с кодами `consent_required` (403 / 422 при регистрации),
`offer_missing`, `offer_outdated` (409); сообщения в `shared/locales/errors`
ru и uz (паритет).

### Тесты

- Регистрация: без обязательных документов → 422; с ними → записи согласий.
- Блокировка: до и после `effective_at`; исключённые роуты; отзыв ПД блокирует,
  повторное принятие снимает; storefront тоже блокируется.
- Оферта: happy-path заказа с акцептом; `offer_missing`, `offer_outdated`;
  существующие тесты checkout публикуют оферту в фикстурах.
- Admin: публикация, неизменяемость опубликованного, незаполненные поля → 422;
  403 для member без права, 401 без токена.
- Изоляция тенантов на `legal_tenant_*`.
- CLI `publish`: идемпотентность, смена текста без версии → ошибка, нет пары
  ru/uz → ошибка.
- Уведомление об отзыве уходит из очереди; паритет шаблонов ru/uz.
- Миграции вверх и вниз; честность манифеста `commerce.cart`.
